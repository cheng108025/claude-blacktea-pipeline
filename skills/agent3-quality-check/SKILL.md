# 品質檢查：可讀、可維護、沒有多餘的程式碼

- **範圍**：呼叫方指定——全專案（全案稽核首輪）／`git diff` 範圍（複審輪、變更輪）／單票異動檔案（票級檢查順帶）。
- **產出**：發現表的列（併入 `04-verify-report.md`，V 編號接續），每條附證據。

## 怎麼做

1. 下面 15 條逐條檢查，每條記：通過／發現／不適用。
2. **工具優先，感覺其次**——品質最容易變成口味之爭，工具輸出是客觀證據：
   - Python：`ruff check .`（未安裝 → `python -m pip install --user ruff` 試一次）、`vulture .`（死碼）。
   - JS／TS：`npx -y eslint .`、`npx -y ts-prune`（未用的 export）、`npx -y jscpd src`（重複程式碼）。
   - 其他語言：用該語言的標準 linter；沒有就用 `grep` 找未引用的符號、重複片段。
   - 工具裝不起來或跑不動 → 在報告標「**未執行工具掃描（原因）**」，改用人工檢查——不准默默跳過。
3. **工單外的功能**（清單第 9 條）要對照規格書「功能清單」與「本版不做」逐項看，不是憑印象。
4. 每個發現一列，格式同 04 報告：`| V-xxx | 實作問題 | Medium／Low | 檔案:行號 | 描述（≤400 字元） | 證據（工具輸出存 evidence/V-xxx-quality.log，只留路徑） | 建議修法（≤200 字元） |`。

## 清單（15 條；與建造者「編碼守則：可維護性」六條對齊——建造者照著寫，這裡就是二次確認）

A. 可讀性
1. 命名一致，跟專案既有程式碼同風格（變數、函式、檔案）。
2. 函式小、單一職責；巢狀深度不超過三層。
3. 選最直白的寫法，沒有炫技寫法。
4. 註解只寫「程式碼本身看不出來的原因」，沒有流水帳、沒有註解掉的程式碼。

B. 可維護性
5. 檔案放置照規格書「技術選型」章的專案結構。
6. 重複邏輯已抽成共用（同一段邏輯出現 ≥2 次＝發現）。
7. 沒有魔術數字／魔術字串（應該是常數或設定）。
8. 錯誤有留下紀錄（log），出問題時查得到。

C. 不必要的程式碼
9. **工單外的功能**：對照規格書「功能清單」與「本版不做」——程式裡有對外行為（API、頁面、指令、選項）是工單沒要求的 → 發現（這是建造者鐵律 1「只做工作單上的任務」的稽核端）。
10. **死碼**：沒有任何地方呼叫的函式／類別／檔案。
11. **未使用的相依**：`package.json`／`requirements.txt` 裡裝了但程式沒 import 的套件；沒用到的 import。
12. 除錯殘留：`console.log`／`print` 除錯輸出、暫時的 TODO 旗標、測試用的硬編碼值。

D. 文件一致
13. `docs/features/*.md` 與 README 描述的行為跟程式一致；沒有殘留舊值（例如改過的 port、改過的欄位名）。

E. UI 一致性（有畫面的專案；依據＝規格書「設計系統」章）
14. 頁面程式碼只用設計系統基座的共用元件與 token：`grep` 裸 `<button`／原生 `<select`／硬編碼色碼（`#[0-9a-f]{3,6}`、`rgb(`）出現在 `components/`／`pages/` 而非基座檔案 → 發現。
15. 每個非同步操作有進行中與結果回饋、每個清單有空狀態（對照狀態矩陣，找呼叫 API 卻沒處理 loading／error 分支的元件）。

## 嚴重度對照 🔧（品質發現只能 Medium／Low，不擋關）

| 發現 | 嚴重度 |
|---|---|
| 工單外的對外功能、文件與實作不符、重複邏輯、死碼、未用相依、UI 一致性（14、15） | Medium |
| 命名、巢狀、魔術數字、註解、除錯殘留 | Low |

## 規則

- **只能給 Medium 或 Low**；**不改變關卡條件**（關卡仍是 Critical=0 且 High=0）。想讓某類升級擋關，改上面的對照表 🔧，不要在這裡自行升級。
- 零發現是有效結果；不為了證明有檢查而製造發現；個人偏好不能單獨成立發現。
- 發現照常收進 04 報告的「已知限制」節，由總指揮逐項抄進 FINAL-REPORT——最後批量修或由使用者決定接受。
