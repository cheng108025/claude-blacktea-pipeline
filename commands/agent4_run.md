使用者附加指示：$ARGUMENTS
（上一行若為空 → 實測全部旅程；有內容 → 原樣轉達給實測員，例如「受影響旅程：J02、J03」——實測員會優先、加深測這幾條，但**仍會全旅程重跑**，不會沿用舊結果。）

**門禁**（只在流水線模式檢查，即 `.pipeline/plan/02-workplan.md` 存在時）：`.pipeline/04-verify-report.md` 應存在且關卡判定為 PASS（扣除 waivers），否則提示先跑 `/agent3_review`，然後停止。單獨模式（沒有 01/02）跳過此檢查。

請使用 agent4-run subagent 對本專案執行完整實測。

實測員完成後，讀 `.pipeline/05-e2e-report.md`，向使用者摘要：

- 關卡判定與旅程結果總覽（PASS 數／總數）
- 覆蓋率缺口與「UI 未實測」清單（如有）
- FAIL 分類與去向（附 E-xxx 編號）：
  - 實作 bug → 提示執行 `/agent2_build 修復輪`。**輪數看報告檔首的「實測輪次」，上限 2 輪**；修完**必須先跑 `/agent3_review agent4 退回：增量複審變更範圍`**（這種複審不佔稽核的 3 輪額度），再回來**重新完整實測（全部旅程重跑）**。超過上限就停，由使用者決定
  - 需求矛盾／缺漏 → 提示跑 `/agent1_plan` 走需求變更子流程
  - 服務起不來 → 提示轉回 `/agent3_review`（可運行性問題）
- 證據位置（`.pipeline/evidence/`）

摘要保持精簡：只講關卡結果、FAIL 去向與需要使用者決定的事；細節留在報告檔，**不整份重述**。

**全部 PASS 且無覆蓋缺口 → 由你（主對話）直接撰寫 `.pipeline/output/FINAL-REPORT.md` 並 commit**，固定章節：

1. 總結：做了什麼、規格定稿版本、共跑了幾輪
2. 通過的檢查：build 整體檢查、稽核關卡（輪次）、實測關卡（輪次）
3. 已知限制：**逐項抄錄** `04-verify-report.md` 的 Medium／Low（含 ID 與檔案位置）＋ 05 報告的「UI 未實測」清單（如有）——一項都不准漏
4. waivers 清單（如有，含理由）
5. 被跳過的階段（如有，註明原因）

寫完 FINAL-REPORT 後提醒使用者：跑一次 `/blacktea_retro` 復盤，把這一案的經驗沉澱進經驗包。
