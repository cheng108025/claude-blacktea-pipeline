# Phase A：定調（第 1 輪只問這三件事）

1. **一句話描述**：這個專案要做什麼、給誰用？（使用者在 `/blacktea_plan` 後面已經寫了描述的話，這題視為已答，從它接著問。）
2. **專案規模**（決定★必滿分的面向）：(a) 小工具——自己用、不用登入、資料簡單；(b) 中大型／正式產品——多人用、有帳號、要正式上線。
3. **技術偏好**：語言／框架／資料庫有指定嗎？有就記下；沒有先不猜——等 Phase B 的「技術棧攤牌」那一輪你會帶著具體建議回來問（見訪談規則）。

# Phase B：訪談迴圈

## 評分表（十面向；每輪更新，展示給使用者看）

十個面向，各給 0 分（還不清楚）／0.5 分（知道一半）／1 分（明確）：

| # | 面向 | # | 面向 |
|---|---|---|---|
| 1 | 專案目標與成功定義 ★ | 6 | 外部整合（第三方 API、登入、金流…） |
| 2 | 目標使用者與使用情境 | 7 | UI/UX 與視覺（有哪些頁面、主要操作流程、**長什麼樣**） |
| 3 | 功能清單與 MVP 範圍 ★ | 8 | 邊界條件與錯誤處理（輸入錯了怎麼辦） |
| 4 | 技術選型 ★（中大型） | 9 | 資安與權限（誰能看什麼、密碼怎麼存） |
| 5 | 資料庫相關（要存哪些資料、怎麼存、存多久） | 10 | 驗收標準（怎樣算做完） ★ |

★ 必滿分的面向（依專案規模）🔧：**小工具**第 1、3、10；**中大型／正式產品**第 1、3、4、10。

計分細則：
- **不適用就跳過**：某面向對這個專案沒意義（例如單機小工具沒有外部整合）→ 記「N/A：原因」，直接算 1 分，不要硬問。小專案不會因此被卡死——9 分門檻對小工具一樣達得到。
- **面向 7 有畫面時**：只問到頁面與流程算 0.5 分，「視覺定調」那一輪問完才算 1 分。
- **使用者說「你決定就好」** → 你選一個合理預設，在規格書的「決策紀錄」寫清楚：選了什麼、為什麼、標「（預設，可改）」，該面向算 1 分。

## 每一題的標準構成

**每一題都要問得很詳細**，讓使用者完全不用猜你在問什麼：

1. **為什麼問**：一句話說明這個決定會影響什麼。
2. **具體選項**：2–4 個，每個附「白話說明＋選它的影響＋適合什麼情況」；其中一個標「（推薦）」，並誠實說明推薦方案的**主要代價**。
3. **舉例**：用這個專案的實際情境舉一個例子，幫使用者想像。
4. **術語隨手解釋**：出現專有名詞就附一句白話（例：「session cookie（讓網站記得你已登入的機制）」）。

範例：

> **Q. 帳號資料要存在哪？**（為什麼問：這決定專案的複雜度，以及之後能不能給多人用）
> - (a) SQLite——單一檔案的資料庫，最省事、不用另外裝東西，適合自己用（推薦）
> - (b) PostgreSQL——正式的資料庫伺服器，適合之後要上線給多人用，但要多裝軟體
> - (c) 純 JSON 檔——最陽春，資料多了會變慢，只適合玩具專案
>
> 以你的記帳工具為例：只有你自己用的話，選 (a) 就夠了。

同一輪題目的獨立性（反例與正解）：
- 反例（不准）：同一輪問「Agent 引擎要用 cron 還是 API」＋「每天幾點跑排程」——引擎若選「手動觸發」，排程題根本不該存在。
- 正解：先單問引擎；拿到答案後，下一輪再問排程（且選項依引擎答案調整）。

## 訪談規則

- 每輪**最多 4 題** 🔧，優先出**選擇題**，開放式問題留給沒辦法列選項的主題。順序永遠「先問會改變其他分支的問題」，避免下游問題白問。
- **同一輪的題目必須彼此獨立**：任何一題的答案會影響另一題「該不該問」或「選項長什麼樣」，就必須把後者拆到下一輪。出題前逐一自問：「如果這題選了 A（或 B、C），另外幾題的問法會不會變？」會變 → 拆開。這條**優先於「一輪 4 題」**——寧可一輪只問 1 題，也不准把有相依關係的題目綁在同一輪。
  - **高影響決策一律單獨問**：技術路線、資料存哪、有沒有帳號系統、要不要做網站這類會分岔出一整串下游問題的決策，單獨一題問清楚再問下一批。
- **能自查的事實自己查**：能從程式庫、文件或工具查證的事（現有專案用什麼框架、某套件支不支援某功能），自己查完直接用——只把真正需要取捨的**決策**留給使用者。
- **每一題都要問得很詳細**，照上面「每一題的標準構成」出題。
- **模糊回答不放行**：使用者答「都可以」「大概吧」→ 不能就這樣記下，追問一次把它變具體；使用者明說「你決定就好」才照預設規則處理。
- **實作偏好隔離**：使用者主動指定做法（「用 XX 套件」「存成 XX 格式」）→ 記進決策紀錄，標「**實作偏好（未驗證）**」——不當場假設它可行、也不當場反駁；留到出工單階段驗證。
- **必問題——視覺定調**（有畫面的專案才問；單獨一輪，排在技術棧攤牌**之前**，因為它決定 UI 樣式方案）。一輪 4 題，全部選擇題：
  1. **風格原型**（三選一，每個附一句「長什麼樣」與適合的情境）：(a) 極簡工具風——大量留白、細邊框、灰階為主、一個強調色，像 Linear／Notion（推薦給自用工具與後台）；(b) 資訊密集儀表板——表格與數字為主、緊湊間距、側欄導覽，像 Grafana／後台管理系統；(c) 消費型活潑——大圓角、鮮明色彩、大字級、卡片與插圖，像一般手機 App。
  2. **亮／暗**：亮色／暗色／跟隨系統（預設亮色）。
  3. **主色**：給 4 個具體色票（例：藍 `#2563eb`、綠 `#16a34a`、紫 `#7c3aed`、中性黑 `#111827`），可自填。
  4. **參考網站或產品**（開放題，可空）：使用者說得出「像 XX 那樣」就記下，設計系統章會以它為依據。
  答案寫進規格書「設計系統」章開頭的「視覺定調」表；使用者說「你決定」→ 預設 (a)＋亮色＋藍，一樣讓他看過。
- **必問題——執行方式攤牌**（不分規模，每個專案都要問；單獨成一輪，排在技術棧攤牌**之前**，因為它決定技術棧表「執行／部署方式」那一列、T01 要檢查什麼、要不要多一張容器化票、README 的啟動指令長什麼樣）。用 AskUserQuestion 問一題、二選一（使用者在 Phase A 已明說的直接填「已確認」不再問）：

  > 這個專案做好之後要 **直接在本機執行**，還是 **用 Docker 打包**？
  > - (a) **本機直接執行**（推薦給自用小工具）——直接用 venv／node_modules 跑：零額外安裝、啟動最快、除錯最直接；代價：換一台機器要重裝環境，路徑與版本容易不一致。
  > - (b) **用 Docker 打包**——產出 `Dockerfile`＋`compose.yml`，`docker compose up -d` 一鍵起，在哪台機器跑都一樣；適合要交給別人跑、要部署到伺服器、或依賴很多的專案；代價：機器要先裝 Docker、建映像多花時間、本機除錯多一層。

  出題前先自查 `docker --version` 與 `docker compose version`：沒裝就把「要先裝 Docker Desktop 並開 WSL 整合」寫進 (b) 的代價。以他的專案舉例（照「每一題的標準構成」）。選 (b) 要在**同一輪**補問三件事（都是 (b) 的子題，不分岔）：對外開哪個 port；哪些資料要留在容器外（資料庫檔、上傳檔、報告——掛 volume）；機密怎麼進去（預設 compose `env_file: .env`，不烙進映像）。使用者說「你決定」→ 預設 (a)，記進決策紀錄標「（預設，可改）」。答案寫進規格書「技術選型」章的「執行／部署方式」列與同章「執行方式」小節。
- **必問題——技術棧攤牌**（不分規模，每個專案都要有這一輪；單獨成一輪，因為它分岔出所有下游問題）：等規模、資料要存什麼、有沒有介面／帳號、外部整合、視覺定調這幾格問清楚後，**你先提出一張具體的分層技術棧表再問**，不是問使用者「想用什麼」：

  | 分層 | 建議 | 為什麼適合這個專案 | 替代方案（一句取捨） |
  |---|---|---|---|
  | 前端 | 例：React 18 + Vite | … | 例：純 HTML+htmx——更簡單但互動多時難維護 |
  | **UI 樣式方案**（前端非 N/A 必填） | 例：Tailwind + shadcn/ui | 例：現成、好看、可改；對得上「極簡工具風」 | 例：MUI——元件更多但風格重、難客製 |
  | 後端 | 例：Node.js 20 + Fastify | … | … |
  | 資料庫 | 例：SQLite | … | 例：PostgreSQL——要多裝軟體，多人上線才需要 |
  | 測試框架 | 例：Vitest | … | … |
  | 執行／部署方式 | 照「執行方式攤牌」的答案填：本機（例：`.venv/bin/python -m app`／`npm run dev`）或 Docker（`docker compose up -d`） | … | 已在攤牌那一輪決定，這裡不再給替代方案 |

  「UI 樣式方案」的建議依視覺定調與前端框架給：React → Tailwind + shadcn/ui（原型 a／c）或 Tailwind + 表格元件庫（原型 b）；Vue → Tailwind + shadcn-vue 或 Naive UI；純 HTML 小工具 → Pico.css／Water.css（零設定）。方案必須是 **npm 可安裝、不靠執行期 CDN** 的（建造者不准引用外部資源）。**沒有這一列，建造者只會寫裸 HTML**——這是前端簡陋的第一原因。

  規則：每一列都要填（不適用寫「N/A：原因」）；建議要對得上前面問到的事實（自己用的小工具不要建議 PostgreSQL＋K8s）；使用者在 Phase A 已指定的分層直接填「已確認」不再問；使用者說「你決定就好」**也要把這張表給他看過一次**，他點頭或改完後標「已確認」，之後規格書「技術選型」章的技術棧表就是這一張原樣搬過去。這一輪的「白話說明」要講到每個選項對**他**的影響（要多裝什麼、以後找人維護容不容易、會不會花錢）。
- **必問題——要不要自動化測試**：通常在問技術選型那一輪問一次：「要不要為核心邏輯寫自動化測試？」附白話說明（測試是長期維護的保險：以後改東西能立刻知道有沒有改壞；代價是開發時間變長。自己用的小工具可以不寫，打算長期維護就建議寫）。答案記進規格書「技術選型」章；要寫的話，工作單就要有對應的測試 ticket 與 DoD。
- 每輪結束做兩件事：(1) 更新評分表給使用者看，標出還差哪幾格；(2) **立刻把已確認的內容寫進 `.pipeline/plan/01-requirements.md`，檔首標「> 狀態：DRAFT」**——這樣對話中斷也不會前功盡棄。
- **使用者說「夠了，開始做」** → 記錄「使用者提前放行」與當下分數，直接進 Phase C（但 Phase D 的自我稽核照跑，不能省）。
- **最多問 8 輪** 🔧：到了上限還沒達標，列出還缺什麼，請使用者三選一：逐項補答／全部授權用預設／中止。
