# 訪談官技能 b：把需求寫成規格書（.pipeline/plan/01-requirements.md）

- **前提**：`01-requirements.md` 已是 DRAFT 且評分表達門檻（總分 ≥ 9.0 且 ★ 滿分），或有「使用者提前放行」／「8 輪上限後授權用預設」的紀錄。不符合 → 停，回報「請先完成訪談（agent1-interview）」。
- **產出**：完整規格書（仍標 DRAFT，直到 Phase E 定稿）；寫完回到 `agent1_plan.md` 接力 Phase D。

## 原則

- 章節**依專案複雜度彈性調整**——下面的菜單是完整菜單，不是硬性規定：小工具可以合併或省略用不到的章，中大型專案可以自行加章（例如部署、效能）。原則：**寧可整章省略，不准某章寫一半**；省略的章在「決策紀錄」用一句話記原因。
- 規格書裡**禁止出現「待定」**——每件事只能是「已確認」（使用者說的）或「預設」（你選的，寫明理由、標註可改）。
- 有寫的每一章都要具體到「下游不需要再猜」的程度——後面的建造者、稽核員、實測員中途沒辦法向任何人提問。

## 六個必備章＋條件式必備章（下游契約：不可省略、章名不可改）

下游 agent 是用「章名」找內容的，不是用編號：

| 必備章 | 誰在依賴它 |
|---|---|
| 專案概述 | HTML 檔名的專案名稱取自這裡 |
| 功能清單（含「本版不做」） | ticket 的「所屬功能」、稽核員架構對照、功能文件 |
| 技術選型 | 建造者的套件依據 |
| 專案資料夾結構 | 建造者檔案放置的依據 |
| 全域驗收清單 | 實測員的唯一劇本 |
| 決策紀錄 | 使用者確認預設值的依據 |
| **設計系統**（有畫面的專案才必備，章名不可改） | 設計系統基座票、建造者前端守則、實測員視覺檢查的唯一依據 |
| **AI相關**（有使用 AI 模型／工具的專案才必備，章名不可改） | 建造者的 AI 呼叫方式與模型 id 依據、稽核員檢查費用控管的唯一依據 |

## 章節菜單 🔧

1. **專案概述**：一句話描述、目標、怎樣算成功（要可驗證，不能是「好用」這種感覺詞）。
2. **使用者與情境**：有哪些角色，每個角色主要拿它做什麼。
3. **功能清單**：MVP 要做的每一項；**同樣重要——「本版不做」清單**（防止建造者自己加戲，也防止稽核／實測把「沒做」誤判成「漏做」）。
4. **技術選型**：開頭必須先放一張**分層技術棧表**，讓使用者一眼看到前端、後端、資料庫各用什麼、為什麼：

   | 分層 | 用什麼（具體名稱＋版本） | 為什麼選它（一句白話理由） | 來源 |
   |---|---|---|---|
   | 前端 | 例：React 18 + Vite | 例：元件生態最大，之後找範例最容易 | 已確認／預設 |
   | UI 樣式方案 | 例：Tailwind 3 + shadcn/ui | 例：對得上「極簡工具風」，元件現成可改 | 已確認／預設 |
   | 後端 | 例：Node.js 20 + Express | 例：與前端同語言，維護成本最低 | 已確認／預設 |
   | 資料庫 | 例：SQLite | 例：單檔零安裝，符合單人使用規模 | 已確認／預設 |

   - 這張表＝訪談「技術棧攤牌」那一輪使用者看過並點頭的那一張原樣搬過來（含測試框架、執行／部署方式兩列），不在這裡另起爐灶。
   - 「來源」欄只能填「已確認」（使用者選的或點頭的）或「預設」（使用者沒看過就由你選的——正常不該出現，出現代表攤牌那一輪漏了）。
   - 不適用的分層填「N/A：原因」（例：純 CLI 工具沒有前端），不准留空。
   - 表格之後再補其餘細節：關鍵套件（寫出具體名稱）、版本要求、dev server 用哪個 port、要不要自動化測試。**專案資料夾結構移到獨立的下一章，這裡不重複寫。**
   - **「執行方式」小節**（訪談「執行方式攤牌」的答案，不可省）：
     - 本機直接執行 → 寫背景啟動指令、port、健康檢查網址。
     - Docker 打包 → 另寫：基底映像（具體 tag，例 `python:3.12-slim`）、對外 port 對應（`主機:容器`）、掛出容器的 volume 清單（資料庫檔、上傳檔、報告等，每個寫主機路徑與容器路徑）、機密注入方式（預設 compose `env_file: .env`，不烙進映像）、健康檢查網址、`.dockerignore` 至少排除 `.git`、`.env`、`node_modules/`／`.venv/`、`.pipeline/`。
5. **專案資料夾結構**：用樹狀圖列出主要目錄與檔案，每項一句話說明放什麼、為什麼放這裡（例：`src/` 原始碼、`tests/` 測試、`data/` 執行期產生的資料檔、`docs/` 功能說明文件）。建造者照這份建資料夾，不自己另外發明佈局；稽核員對照它檢查有沒有亂放檔案。
6. **資料模型**：每個要存的東西（實體）有哪些欄位、什麼型別、哪些必填／不可重複、彼此的關聯。**用 SQL／關聯式資料庫存資料的專案，要把實際的表格定義寫出來**（像 `CREATE TABLE` 一樣具體：表名、每欄名稱與型別、主鍵／外鍵、索引），並用白話解釋每張表存什麼、為什麼需要——不是只列抽象的「實體」。非關聯式儲存（檔案、KV、JSON）也要同等具體：存成什麼格式、放在哪個路徑。
7. **介面契約**（有 API 或 CLI 介面才需要；**這章定義「外部怎麼跟這個系統打交道」的精確形狀**——建造者照這份寫介面、票級檢查與稽核員照這份核對有沒有做到，不用去猜參數叫什麼、回應長什麼樣）：
   - Web/API 專案：每支 API 的方法、路徑、請求格式、成功回應範例、錯誤碼與錯誤回應格式。
   - CLI 專案：每個指令的參數、輸出格式、退出碼。
7b. **AI相關**（有使用 AI 模型／工具的功能才需要；章名不可改——建造者靠它知道怎麼呼叫、稽核員靠它檢查模型 id 與費用控管有沒有落實）：
   - **怎麼呼叫**：CLI 指令或 API 呼叫方式（例：`claude -p --model claude-sonnet-5`、`codex exec`）、背景執行還是互動、逾時秒數。
   - **用了哪些 AI 工具／模型**：寫**完整模型 id**（不用會隨時間漂移的別名，例寫 `claude-sonnet-5` 不寫 `sonnet`），每個呼叫點用哪個模型、做什麼任務。
   - **費用性質**：用既有訂閱／CLI 帳號、免費額度內、還是另計 API 費用；呼叫頻率（例：每日一次、隨選觸發）；大致的輸入規模（寫量級即可，不用算到小數點）。
   - **失敗處理**：沒回應、逾時、額度用盡時系統怎麼表現（報錯？跳過？用舊資料？）。
   - 沒有用到 AI 的專案 → 整章省略，在「決策紀錄」記一句「本專案不使用 AI」。
8. **頁面清單與流程**（有畫面的專案）：每頁的用途、上面有什麼、頁面之間怎麼跳轉。
8b. **設計系統**（有畫面的專案必備；這一章決定「長什麼樣」，下游沒有別的依據）：
   - **視覺定調表**：風格原型、亮／暗、主色、參考產品（訪談「視覺定調」那一輪的答案原樣搬過來）。
   - **設計 token**（具體值，建造者會原樣寫進 CSS 變數／框架設定）：色彩（主色、主色 hover、背景、表面、邊框、文字主／次、成功／警告／危險）、字級階（例：12/14/16/20/24/32）、間距階（4 的倍數：4/8/12/16/24/32）、圓角、陰影一到兩階、字型堆疊（含 CJK 後備字型）。
   - **版面骨架**：外殼（頂欄／側欄／無）、內容最大寬度、卡片網格欄數與間距、各頁大致區塊排列（用文字或 ASCII 示意）。
   - **元件清單**：本專案會用到的元件與變體，至少含 Button（primary／secondary／danger／disabled）、Input／Textarea／Select（含錯誤態）、Card、Badge／狀態標籤、Tabs、Dialog、Toast、EmptyState、Skeleton／Spinner；每個元件一句「用在哪」。
   - **每頁狀態矩陣**（最重要，建造者最常漏的就是這個）：頁面 × 狀態（初次載入／空資料／有資料／操作進行中／成功回饋／錯誤／disabled 與原因）；每一格寫清楚畫面顯示什麼、文案是什麼。
   - **文字與回饋規則**：CJK 名稱不折行（溢出用省略號＋title）、數字等寬、每個非同步操作要有進行中與結果回饋、破壞性操作要二次確認、錯誤訊息的統一長相。
   - **無障礙基本**：鍵盤可操作、焦點可見、文字對比 ≥ 4.5:1、表單有 label。
   - **UI 原型**：指向 `.pipeline/plan/ui-prototype.html`（Phase E 產出、使用者看過點頭）——UI 票的 DoD 會寫「與原型對照」。
   - 小工具也不准省略這章，只准縮短（token ＋ 元件清單 ＋ 狀態矩陣三段是底線）。
9. **邊界條件與錯誤處理**：空值、超長、格式錯誤的輸入各要怎麼回應；錯誤訊息的統一呈現方式。（小專案可以不獨立成章，直接寫進「全域驗收清單」。）
10. **資安與權限**：哪些操作要先登入、密碼怎麼存、金鑰類（.env）怎麼管理。
11. **全域驗收清單**（**實測員的唯一劇本，必須自給自足**——它不讀其他章、不讀程式碼）：
    - 每個角色至少一條完整旅程（例：註冊→登入→核心操作→登出），每條旅程寫出：**具體步驟、具體的測試輸入值、可直接判對錯的預期結果，以及驗證方法**（用哪個網址／指令／畫面操作去確認，不是只寫「對不對」）。有計算的功能要給數字基準（例：記帳 100／250／50 三筆後，月報表要顯示 400）。
    - 全部頁面／API 的完整列表，且必須跟「功能清單」「介面契約」「頁面清單」（後兩章有寫的話）完全一致（不能多也不能漏）。
    - 把「邊界條件與錯誤處理」章每個輸入欄位的邊界行為抄進來（或該章省略時直接寫在這裡）：接受的上限、會拒絕的條件、預期的錯誤訊息長相。
12. **決策紀錄**：所有「（預設，可改）」的集中列表、「實作偏好（未驗證）」項目、被省略的章與原因——使用者最後就是看這張表決定要不要改。
13. **問答紀錄與最終評分表**。

## 怎麼寫

1. 照菜單逐章寫（技術選型章開頭必放分層技術棧表；有畫面就必有「設計系統」章；有使用 AI 工具就必有「AI相關」章；全域驗收清單必須自給自足）。
2. 決策紀錄集中列出：所有「（預設，可改）」、「實作偏好（未驗證）」、被省略的章與原因。
3. 文末放問答紀錄與最終評分表。
4. 寫完回到 `~/.claude/agents/agent1_plan.md`，接力 Phase D（Read `~/.claude/skills/agent1-tickets/SKILL.md`）。
